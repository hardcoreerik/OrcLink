# v0.1 Scope

## Outcome

v0.1 proves one daemon, a small capability model, durable command/audit state, supervised adapters, one deterministic demo workflow, and an M5Tab5 integration proof. It is not a complete automation platform.

## Adapter scope

### Windows host

Read host/process/service status, stream approved logs, and start/stop/restart allowlisted services. Arbitrary shell execution is excluded.

### Ollama

Read server/model status, list installed/running models, start a bounded generation, cancel it, and report available timing/token metrics. Model deletion and uncontrolled downloads are excluded.

### Generic ESP32

Discover serial devices, bind a stable approved identity, ingest structured serial/MQTT telemetry, send schema-defined commands, and reconnect. Generic firmware flashing is limited to the first demo's approved artifact and explicit approval.

### Klipper through Moonraker

Read printer/job/temperature state and exercise safe development/test commands. Start/cancel/emergency operations remain disabled until policy, verification, and test-hardware safeguards are demonstrated.

## M5Tab5 support scope

- Complete hardware/runtime validation report for the exact target unit.
- Pair one device with `orclinkd` using a stable cryptographic identity.
- Register the device and a minimal verified capability set.
- Stream health plus one verified input/sensor signal.
- Display daemon connection state, a node-status list, one alert, and one approval request.
- Journal events offline, clearly display degraded state, and deduplicate them after reconnect.
- Run one pre-installed, low-risk offline workflow with bounded parameters.
- Demonstrate that offline state cannot authorize a centrally gated command.

Native versus web UI and exact peripheral transports remain validation-driven.

## Out of scope

- Public Internet access, cloud accounts, multi-tenant operation, plugin marketplace.
- Autonomous AI execution or arbitrary commands/scripts.
- General workflow DAGs, distributed transactions, or universal rollback.
- SDR signal processing, SatDump orchestration, Meshtastic parsing, Bluetooth peripheral control, DMX timing, laser output, BrightSign control, or mobile apps.
- Production control of hazardous, high-temperature, moving, transmitting, or intense-light equipment.

## Milestones

1. **Contracts:** node, event, capability, command, manifest, error, and risk schemas agreed.
2. **Simulator:** daemon handles simulated nodes, lifecycle, timeout, cancellation, verification, restart reconciliation, and SQLite history.
3. **Host/Ollama:** two real adapters and Control Room operations/timeline views.
4. **M5Tab5 validation:** exact hardware report and thin communication/UI proof.
5. **ESP32 demo:** approved firmware-test workflow with serial capture and verification.
6. **M5Tab5 resilience:** pairing, offline journal, bounded local workflow, reconnect sync, approvals UI.
7. **Klipper read-only:** persistent state and alert ingestion on test hardware.
8. **Release gate:** targeted tests, threat review, recovery exercise, and documentation truth sync.

## Acceptance criteria

- A fresh local install starts without cloud access.
- Unknown devices and undeclared capabilities are quarantined/denied.
- Every command has requester, target, arguments, risk, decision, timestamps, and terminal or uncertain status.
- Daemon and adapter restarts do not silently duplicate consequential commands.
- The first demo identifies the intended ESP32, requires flash approval, captures logs, verifies firmware after reboot, and reports the exact failed step.
- One paired M5Tab5 satisfies the support scope above with hardware facts recorded as measured evidence.
- Control Room and M5Tab5 show consistent command and alert state after reconnection.
- Targeted automated tests cover lifecycle, policy denial, idempotency, and sync deduplication; hardware checks record exact devices and steps.
- No claim of safety depends only on application software where a physical safeguard is required.
